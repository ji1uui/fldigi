# ADR-005: Plugin の隔離 — 障害を封じ込め、将来のサブプロセス化を妨げない

- 状態: 採用 (Phase 0 / draft)
- 対応する Baseline: v1.1 §11.1, §14 Z-04, §19 ADR-005, ADR-001
- 実装: `units/PluginApi.pas`, `units/PluginHost.pas`
- 検証: `test/test_plugin.lpr`

§11.1 は二つのことを言っている。

> API は将来のサブプロセス化・Sandbox 化を妨げない。
> Plugin 障害は Core や他 Plugin へ波及させない。

前者は「いまはやらない」ことの約束であり、後者は「いまやる」ことである。
両方をどう受けたかを書く。

## 「妨げない」を検証可能にする

この種の原則は、宣言しただけでは守られない。**守られていないことに
気づけない** からである。破り方は決まっていて、境界を越える型に

- Core のドメインオブジェクトへの参照 (`TQsoEntry`, `TModem`, `TEventBus`)
- ポインタ、ファイルハンドル、クロージャ
- そのほか直列化できないもの

のどれかが混ざった瞬間に、二度と別プロセスへ出せなくなる。しかも
その時点では何も壊れないので、Phase 5 になって初めて分かる。

そこで境界を越える型を **バイト列に往復できること** で定義した。
`EncodeMessage` / `DecodeMessage` / `EncodeDescriptor` / `DecodeDescriptor`
がその往復で、`test_plugin` の 3 番がすべての境界型について往復を固定
している。誰かが将来 `TPluginMessage` にオブジェクト参照を足せば、
**その時点で** テストが落ちる。

形式は長さ前置・リトルエンディアン。値の中身を見ずに長さだけで切り出せる
(ADIF と同じ考え方)。壊れた入力で落ちないこと・巨大な確保をしないことも
測っている ── 別プロセス化したら向こう側は信用できない入力元になるので、
そこを緩めたまま出すわけにいかない。

### 例外: `TPluginHostContext`

これだけはクラス参照で渡る。RPC でいうスタブに当たり、別プロセス化した
ときは同じ宣言の「向こう側へ中継する実装」に差し替わる。したがって
**ここに置いてよいのは引数と戻り値がすべて値であるメソッドだけ** である。
Core のオブジェクトを返すメソッドを足した瞬間に、この例外が例外でなくなる。

### Data Plane はここを通らない

ADR-001 のとおり、音声/IQ/スペクトラムはメッセージにしない。
`TModemPluginBase.ProcessBlock` に渡す配列は
**呼び出しの間だけ有効で、Plugin は保持してはならない** という規約にした。

この規約があるから、別プロセス化のときに共有メモリのリングへ置き換え
られる。保持を許すと置き換えられない。波形をメッセージにしてしまっても
同じく置き換えられない (毎ブロック直列化する羽目になる)。中身は Phase 2
で詰めるが、境界の形はいま決めておく必要がある。

## 「波及させない」を実際にやる

Plugin への呼び出しは **すべて関門を通る**。`TPluginRegistry` の
`SafeInitialize` / `SafeShutdown` / `SafeHandle` の三つで、ここ以外から
`slot.Plugin.XXX` を呼んではならない。三つに分かれているのは Pascal に
閉包が無いためで、意図としては一つの関門である
(失敗の数え方と時間の測り方は `BeginCall` / `EndCallOk` / `EndCallFault`
に集約してある)。

関門がやること:

1. 例外を受け止め、呼び出し元へ投げ返さない。
2. 連続失敗を数え、続いたら隔離する。
3. 所要時間を測り、予算を超えたら記録する。

`DispatchMessage` は失敗した Plugin の次へ進む。`test_plugin` の 5 番は
壊れた Plugin を **健全なものの間に挟んで** 登録し、後ろの Plugin にも
届くことを確かめている。先頭や末尾に置くと、順序の都合で通っただけかも
しれない。この関門を外すと、テストは失敗ではなく **プロセスごと落ちる**
(反証で確認済み)。

`Describe` も `Handles` も Plugin のコードなので関門の中で呼ぶ。
自己申告の最中に例外を投げる Plugin は受け入れない。初期化に失敗した
ものは登録を残したうえで呼ばない ── 黙って消えるより状態が見えるほうが
診断しやすいが、半端な状態のまま呼ぶと次の失敗の原因が初期化なのか
処理なのか分からなくなる。

## 隔離は「連続」失敗で判断する

通算の失敗数で切ると、長時間動いている健全な Plugin がいつか必ず
隔離される。逆に「たまに失敗する」を許し続けると、壊れた Plugin が
毎回例外を投げながら永久に呼ばれ続ける。circuit breaker と同じで、
成功したら数え直し、連続したときだけ切る (既定 3 回)。
運用者は `Revive` で戻せる。

## 時間の予算については正直に書く

同一プロセス内では、時間を **測ることはできるが止めることはできない**。
Plugin が無限ループに入れば、呼んだスレッドは戻ってこない。
Z-04 の deadline を Plugin に対して本当に強制するには、別プロセスに
出して落とせるようにするしかない。

いま測っているのは「その必要があるかどうかを判断するための材料」であり、
強制ではない。`plugin.call` メトリクスに予算 (既定 10 ms) を設定し、
超過を `ocdPluginSlow` として記録する。

**これが ADR-005 の「将来サブプロセス化を妨げない」が必要な理由そのもの
である。** 妨げないだけでは足りず、いずれ実際に出すことになる。

## Plugin になりすませない

Plugin が Event Bus へ発行するとき、発行元 (`Source`) は Plugin の Id で
**上書きする**。名乗らせない。名乗らせると Plugin が Core や他 Plugin に
なりすませてしまい、記録を見ても誰が出したのか分からなくなる。

記録 (`Log`) と発行 (`Publish`) は別の道筋なので、両方について
固定してある (片方だけ守っても意味がない ── これは反証で実際に
見落としていたのを見つけた)。

同じ理由で、設定の読み出しは Plugin の Id で名前空間が切られる。
Plugin は他の Plugin や Core の設定を読めない。

Plugin が Event Bus へ載せられるのは汎用のテキスト通知だけで、
Core 固有の種別 (復調・リグ) は名乗れない。文字列長にも上限を置いた
(Control Plane に大きなものを流させない / ADR-001)。

## いまやっていないこと

- 動的ライブラリの読み込み (Phase 5 の Modem Plugin SDK)
- 実際のサブプロセス化・Sandbox 化
- Plugin の署名・権限モデル (ADR-003 の L6 と合わせて検討する)

Phase 0 で決めるのは「何が境界を越えるか」であって「どうやって
読み込むか」ではない。
