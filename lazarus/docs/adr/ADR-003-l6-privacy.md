# ADR-003: L6 Persistent Memory — Opt-in、管理必須、暗号化可能な保存設計

- 状態: 採用 (Phase 0)
- 対応する Baseline: v1.1 §8 Context Engine, §8.1 L6 Persistent Memory, §19 ADR-003
- 実装: `units/ContextMemory.pas`, `units/SecureStore.pas`, `units/CryptoPrimitives.pas`
- 検証: `test/test_context_memory.lpr`

§8.1 は 4 つを課している。うち 3 つ目が「**暗号化の実装方式は Phase 0 で
決定する**」であり、この ADR の主眼はそこにある。

| §8.1 の要求 | どう受けたか |
|---|---|
| 保存はユーザー操作または明示的承認を前提とし、既定では L5 内で完結する | `TContextMemory` の承認関門 |
| View / Edit / Delete / Export / Import できる | 同クラスの API として実装 |
| 保存形式は将来暗号化を可能にする設計とする | `SecureStore` の容器 |
| Name、QTH 等は最小限保持を原則とする | 包括承認では上がらない扱い |

## 決めたこと 1: 承認を注意書きではなく構造にする

L5 への記録 (`NoteL5`) と L6 への昇格 (`PromoteToL6`) を **別の入口** にした。
同じ関数に引数で分けると、呼び出し側の書き忘れが素通りする。

`PromoteToL6` は承認が無ければ何もせず、理由を返す。

```
l6Denied        → promDeniedByConsent
l6AskEveryTime  → promNeedsApproval          (既定)
l6Granted       → 個人情報なら promNeedsExplicitPersonal
```

既定は `l6AskEveryTime` である。`l6Granted` を既定にすると
「デフォルトでは L5 内で完結する」に正面から反する。

## 決めたこと 2: 個人情報は包括承認では上がらない

`Name` / `QTH` / `GridSquare` / `Note` は、包括承認 (`l6Granted`) があっても
**項目ごとの明示承認** を別に要求する。「一度 OK と言ったら以後すべて保存」
は §8.1 の最小限保持と相容れない。

コールサインを個人情報に含めていないのは、免許情報として公開されている
ためである。ただしコールサインと結び付いた名前・所在地は公開情報ではない。
`Note` は何が書かれるか分からないので個人情報として扱う。

削除すると承認も取り消す。項目だけ消えて承認が残ると、次に同じ値が
抽出されたとき黙って保存されてしまう。

## 決めたこと 3: 暗号化の実装方式

ここが §8.1 が Phase 0 に求めている決定である。

### 3-1. FPC が持っているもので済ませることはできない

FPC 3.2.2 が同梱しているのは MD5 / SHA-1 / HMAC-MD5 / HMAC-SHA1 /
Blowfish / base64 だけである。**SHA-256 も AES も PBKDF2 も CSPRNG も無い。**

同梱の Blowfish は使わない。`TBlowFishEncryptStream` は 8 バイトごとに
独立して暗号化しており、連鎖も IV も無い ── つまり **ECB** である
(`blowfish.pp` の `Write` を参照)。同じ平文ブロックが同じ暗号文ブロックに
なるので、ログのような繰り返しの多いデータでは構造がそのまま漏れる。
加えて Blowfish はブロック長 64 bit で、認証も付かない。2026 年に新規採用
する選択肢ではない。

### 3-2. 自分で書いてよいものと、書いてはいけないもの

**ハッシュ・MAC・KDF は自前で書いた。**
公開試験ベクタ (FIPS 180-4 / RFC 4231 / RFC 8018) が正しさを完全に固定
できるためである。合っているかどうかを「合っている」と断言できる。
`test_context_memory` の 1 番が 12 本の既知解を照合している。

**ブロック暗号・AEAD は自前で書かない。**
試験ベクタが通ることと安全であることが別だからである。サイドチャネル、
モードの誤用、nonce の再利用は、往復試験ではいっさい検出されない。
「暗号のように見えて暗号でないもの」を作る、いちばん典型的なやり方が
これである。

### 3-3. 採用する方式 (実装は Phase 1 以降)

| 役割 | 第一候補 | 対案 |
|---|---|---|
| 暗号 | AES-256-GCM | XChaCha20-Poly1305 |
| 鍵導出 | Argon2id | PBKDF2-HMAC-SHA256 (600,000 回以上) |
| 完全性 | AEAD の認証タグ | ─ |
| 鍵の出所 | 運用者のパスフレーズ | ─ |

条件:

- **AEAD であること**。暗号化のみ (認証なし) の方式は採らない。
  改竄検出が無い暗号は、あるつもりで無い。
- **実装は検証済みの外部ライブラリから取る**。自前で書かない。
  どのライブラリを採るか (libsodium 等) は Phase 1 の依存関係の話であり、
  ここでは決めない。決めるのは「自前で書かない」ことと「方式」である。
- PBKDF2 は既に実装済み (`CryptoPrimitives`) なので、Argon2id が
  手に入らない環境でも鍵導出は成立する。

識別子は `SecureStore` に予約済みで、ファイルに書かれる数値は
**決して振り直さない**。

### 3-4. 正直に書いておく取り引き

パスフレーズによる暗号化は、**毎回入力を求める** ことと引き換えである。
自動的に開くようにすれば鍵はどこかに置かれ、その置き場所が守られて
いなければ暗号化の意味は薄れる。OS の鍵保管 (libsecret / DPAPI /
Keychain) を使うのが筋だが、これはプラットフォームごとの実装であり、
Phase 1 の Modern Runtime で扱う。

したがって L6 の暗号化は **既定で有効にはしない**。既定で有効にすると、
起動のたびにパスフレーズを求められるか、鍵が平文で置かれるかの
どちらかになる。opt-in である (§8.1 の Opt-in はここにも効く)。

### 3-5. 乱数

`SecureRandomBytes` は OS の CSPRNG から取り、取れなければ **例外にする**。
`Random()` に落ちる実装にしてはならない。予測可能な salt と nonce は、
暗号を入れた瞬間に静かにすべてを無効にする。
「弱い乱数で動き続ける」より「動かない」ほうが安全である。

現在 Unix (`/dev/urandom`) のみ実装。他のプラットフォームは例外を投げる
(Windows: `BCryptGenRandom` / macOS: `SecRandomCopyBytes` を Phase 1 で足す)。

## 決めたこと 4: 容器を最初から通す

「後で暗号化できる設計」が破られるのは、たいてい次の形である。

- 平文のまま素朴に保存し、後から「先頭に鍵情報を足そう」とする →
  既存ファイルが読めなくなり、移行コードが要る
- 暗号方式を決め打ちで埋め込む → 後で変えられない
- 暗号化された古いファイルを、新しい版が平文として読んでしまう

だから最初から容器 (`SecureStore`) を通す。いま中身は平文 (`cipher = none`)
でも、容器の形は同じである。移行は要らない。

```
0   magic "L6ST" | 4  version | 6 cipher | 7 kdf | 8 iterations
12  salt(16)     | 28 nonce(12)          | 40 payload length
44  payload...   | 末尾 tag(32)
```

`salt` と `nonce` は `cipher = none` では使わないが場所を確保してある。
ここで乱数を要求しないのは、乱数源の無い環境で平文保存すらできなく
なるのを避けるためである ── 乱数が要るのは暗号を入れてからでよい。

### 4-1. 知らない暗号方式のファイルは開かない

**これがこの容器でいちばん重要な性質である。** 復号できない方式の
ファイルを平文として読み出すと、暗号化された個人情報をそのまま表示する
ことになる。個人情報を扱う保存先で、いちばんやってはいけない壊れ方である。

`test_context_memory` はこれを、**封が正しい** 偽の暗号化ファイルを
組み立てて確かめている。cipher id を書き換えるだけではタグ照合で弾かれ、
cipher の検査が無くても通らない ── それでは検査が効いているか
確かめられないためである。

### 4-2. タグはヘッダを含めて計算する

含めないと cipher id を書き換えられ、「暗号化済み」を「平文」と偽れる。
AEAD でいう AAD にあたる。

`cipher = none` のときのタグは **鍵の無い SHA-256 チェックサム** である。
破損と、気づかない書き換えを検出する。これは秘匿でも認証でもない ──
誰でも中身を書き換えてタグを付け直せる。そう書いておかないと
「タグが付いているから守られている」と誤解される。

## 代わりに検討して採らなかった案

**案A: いまは平文で保存し、暗号化は必要になってから容器ごと導入する。**
§8.1 が「保存形式は将来暗号化を可能にする設計とし」と書いているのは、
まさにこれを禁じている。後から容器を被せると既存ファイルの移行が要る。

**案B: 同梱の Blowfish で今すぐ暗号化する。**
ECB で認証も無いので、暗号化したという事実だけが残って中身は守られない。
「暗号化済み」と表示することが害になる。

**案C: AES を自前で実装する。**
試験ベクタは通せるが、それは正しさの一部でしかない。ここで線を引く
理由は 3-2 に書いたとおり。

## いまやっていないこと

- 実際の暗号化 (方式は決めた。実装は外部ライブラリ選定後)
- OS の鍵保管との連携 (Phase 1)
- Unix 以外の乱数源 (Phase 1)
- 管理 UI そのもの (API は揃えた。画面は Phase 1 の UI 分離と合わせる)
