# ADR-011: 交信データモデルは ADIF から独立させ、ADIF は外側のアダプタにする

- 状態: 採用 (Phase 0)
- 対応する Baseline: v1.1 §13.1〜§13.4, §11 Plugin, §14 Z-05, CNT-010
- 実装: `units/QsoModel.pas`, `units/QsoAdifAdapter.pas`
- 検証: `test/test_qsomodel.lpr`

## 何が問題だったか

これまでのログは `QsoLogbook.TQsoRecord` で、ADIF の 12 項目を平坦に並べた
構造体だった。全項目版の `AdifFile.TAdifRecord` でも固定 61 項目である。
どちらも「ADIF の形がそのまま内部の形」になっている。

v1.1 §13.4 はこれを明確に否定している。

> 内部データモデルは ADIF そのものに制約せず、
> Rich Internal Model ↔ ADIF Adapter という関係を維持する。

制約したままだと、後段のフェーズで次が成立しない。

| 要求元 | 固定項目の構造体では表せないもの |
|---|---|
| §13.1 / Phase 4 | 値ごとの「出所」と「確定段階」。抽出した候補と運用者が確定した値の区別 |
| §13.2 / Phase 6 | 1 交信に対する複数の確認経路。`QSL_RCVD` 1 列では「LoTW は照合済だが紙は要求中」を表せない |
| §13.3 / Phase 6 | 局所 ID と改訂番号。どちらが新しいか判定できないと同期の競合を解決できない |
| §11 / Phase 5 | Plugin が Core を改修せずに項目を足すこと |
| CNT-010 / Phase 6 | コンテストごとに違う交換項目 |

さらに、いま既に起きている実害がある。`TAdifDatabase.LoadFromFile` は
`FieldIdFromTag` が -1 を返したタグ、つまり 61 項目に無いタグを黙って捨てる。
ADIF は 150 以上の標準項目と `APP_` 接頭辞の自由項目を持てる書式なので、

> 他のログソフトで作った ADIF を読み込んで書き戻すと項目が減る

という壊れ方をする。取り込み → 書き戻しは日常的な操作で、しかも
**減ったことに気づけない**。`test_qsomodel` の 7 番はこの損失を
`FieldIdFromTag('SIG_INFO') < 0` として固定した上で、新モデルでは
往復しても残ることを確かめている。

## 決めたこと

### 1. 項目は「名前引きの集合」にする

固定の構造体をやめ、`TQsoFieldSet`（文字列キー・挿入順保持）にした。
Plugin もコンテストの交換項目も未知の ADIF タグも、Core を触らずに載る。
よく使う名前は `QSO_CALL` 等の定数で与えるので、中核のコードが文字列を
直書きすることにはならない。

挿入順を保つのは書き出しの再現性のためである (Z-05)。JSON オブジェクトの
キー順は仕様上意味を持たないので、順序を意味に使うところは配列にした。

### 2. 値は「出所・確定段階・Evidence を伴う値」にする

`TQsoField = (Value, Origin, State, Evidence, HasEvidence)`。

これが §13.1 の
`Candidate → Confidence → Operator Confirmation → Committed QSO`
の前提である。同時に運用上の安全にもなっていて、`SetCandidate` は
確定済みの項目を上書きしない。受信中に抽出結果が運用者の入力を
勝手に書き換える、という壊し方をしない。

`Evidence` は **Confidence ではない** (§7 CF-01 / ADR-002 と同じ区別)。
ここに入るのは校正されていない内部尺度で、`P(correct|c) ≈ c` を満たす
確からしさへの変換は Phase 4 の責務である。この層では変換しない。

### 3. QSL 確認は交信とは別のオブジェクトにする

`TQslConfirmation` を 1 交信に何本でもぶら下げる。紙・ビューロー・
ダイレクト・eQSL・LoTW・ClubLog・QRZ がそれぞれ独立に進む。

### 4. 局所 ID と改訂番号を持つ

`NewQsoId` は時刻＋連番＋乱数で、外部サービスに依存せずオフラインで
発行できる (§13.3 Local authoritative)。`Revision` は変更のたびに増え、
provider ごとの `SyncedRevision` と比較することで
「送った後に手元が変わったか」が判定できる。

これは読み込み時に落とし穴がある。`AddQsl` / `Sync` は `Touch` を呼んで
`Revision` を進めるので、読み込みで先に `Revision` を復元すると保存時と
ずれる。ずれると `NeedsSync` が毎回「変わった」と言い、同期が止まらなく
なる。よって復元は QSL と同期状態を入れ終えた **最後** に行う。
`test_qsomodel` の 6 番がこれを固定している。

### 5. ADIF は外側のアダプタにする

`QsoModel` は `AdifFile` に依存しない。両方を知るのは
`QsoAdifAdapter` だけである。

アダプタは ADIF テキストを **直接** `TQsoStore` へ読み込む。
`TAdifRecord` を経由すると 61 項目で漉されてしまい、上に書いた損失が
そのまま残るためである。既存コード (ContestLog / QslUpload) 用に
`EntryToAdifRecord` / `AdifRecordToEntry` も用意したが、こちらは
損失があるので `AdifRecordDropCount` で件数を数えられるようにした。
呼び出し側が黙って失わずに済む。

対応の要点:

- Plugin 項目は `APP.VENDOR.NAME` ↔ `APP_VENDOR_NAME`。
  内部側の区切りは `.` だけに統一する (`.` と `_` を混ぜると ADIF 側で衝突する)。
- QSL 系タグ (`QSL_SENT` / `LOTW_QSL_RCVD` 等 16 種) は
  `TQslConfirmation` が受け持ち、項目集合には入れない。
  両方に持つと書き戻しで 2 回出て、他ソフトが読んだときに壊れる。
- 新しい読み込み経路では `<EOH>` を必須にしない。ADIF 仕様上ヘッダは
  省略でき、交換用に本体だけを渡してくる実装がある
  (既存の `TAdifDatabase.LoadFromFile` はこれを例外にしてしまう)。

## 保たないもの (明示しておく)

- ADIF のデータ型指示子 (`<NOTES:12:M>` の `M`)。項目名から決まる助言的な
  情報で、値そのものは往復しても変わらない。
- 元ファイルでのタグの出現順。書き出しは内部の挿入順になる。
  「読んだ順」ではなく「モデルの順」で安定させるほうが Z-05 に適う。

## 代わりに検討して採らなかった案

**案A: `TAdifRecord` に項目を足していく。**
足した瞬間は済むが、次に知らないタグが来ればまた同じことになる。
Plugin (§11) は Core を改修せずに項目を足せることが要求なので、
enum を増やす方式では原理的に満たせない。

**案B: 未知の項目だけを別の「その他」欄に文字列で溜める。**
往復はできるが、その中身に対して検索も条件分岐もできない。
コンテストの交換項目 (CNT-010) が「その他」に落ちると使えない。

**案C: 最初から SQLite にする。**
Phase 6 では妥当だが、Phase 0 で永続化の技術選定まで決めると
モデルの形の議論が実装都合に引きずられる。いまは JSON で保存し、
形式に `version` を持たせて後から移行できるようにした。

## 影響

- `QsoLogbook.TQsoRecord` は当面そのまま残る。UI がまだこれを使っている
  ためで、置き換えは Phase 1 (UI 分離) と合わせて行う。
- 既存の `AdifFile` は変えていない。公開したのは `FieldIdFromTag` だけで、
  これは「写せない項目を呼び出し側が数えられるようにする」ためである。
