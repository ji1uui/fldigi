# ADR-009: 並行性は要求から導き、並列性は実測から導く

- 状態: 採用 (Phase 0)
- 対応する Baseline: v1.1 §1.1 設計憲章, §5 X-01〜X-09, §14 Z-04
- 影響: X-02 / X-03 の実装時期、C-10 の優先度
- 検証: `test/test_realtime.lpr`, `test/test_evidence.lpr`

## 決定

> **並行性 (concurrency) は要求から導く。並列性 (parallelism) は実測から導く。**
>
> スレッドは音声・CAT・バックグラウンド解析の 3 本を上限とし、
> 増やすときは遅延またはジッタの実測を根拠とする。
> ハードウェア活用そのものを目的にしない。
>
> ただし、状態をインスタンスに閉じ込める規律は常に守る
> （後から並列化する余地を捨てないため）。

## 背景: 実測すると並列化の動機がない

| 対象 | 1 コアに対する使用率 |
|---|---|
| RTTY 復調 1 本 | **0.82%** |
| CW 復調 1 本 | **0.35%** |

1 コアで RTTY 復調器を約 120 本回せる。単一モデムの復調に並列化は要らない。

Phase 3 以降の機能に当てはめても、必要なのは多くの場合「コア」ではなく
「構造」だった。

| 機能 | 必要な計算量 | 本当に要るもの |
|---|---|---|
| D-03 複数信号同時 decode（10 信号） | 8%。1 コアで足りる | リングバッファからの分配 |
| C-07 Replay Decode（30 秒巻き戻し） | 処理は 0.25 秒 | 生音声を止めないワーカー 1 本 |
| C-06 複数 Decoder 並列評価（3 戦略） | 2.5%。1 コアで足りる | 戦略の切り替え機構 |

## 「スレッドセーフ」を方針の名前にしない

スレッド安全性はスレッドを持ってしまったから払う代償であり、目標ではない。
これを方針名にすると「スレッドを足す → 安全にする」という順序になりやすく、
逆である。方針は**スレッドを増やさないこと**であり、安全性はその結果得る。

| | 何のため | 判断 |
|---|---|---|
| 並行性 | 音声が UI で止まらない、CAT が音声を止めない | **要求。今持つ**（B-05 / B-06） |
| 並列性 | スループット | **実測で足りなくなってから** |

現在の 2 スレッド（`ModemEngine`、`RigPollThread`）はいずれも並行性であり、
並列性はゼロである。これは妥当な状態と判断する。

## 判定基準を CPU 使用率から遅延へ移す

堅牢性・デコード性能・UI の快適さを壊すのは CPU 不足ではなく**遅延とジッタ**
である。平均が 1% でも、たまに 100 ms かかれば underrun する。

そこで判定を「1 ブロックの処理時間 / deadline」に置いた
（`test_realtime.lpr`）。8000 Hz・512 サンプルなら deadline は 64 ms。

```
RTTY: 平均 1.12% / p99 1.24% / 最悪 1.87%
CW  : 平均 0.55% / p99 1.11% / 最悪 1.94%
```

最悪値だけは実行ごとに 3 倍近くばらつく（OS のスケジューラに割り込まれる）。
平均と p99 は安定するので厳しめ（8〜9 倍の余裕）、最悪値は緩め（10 倍の余裕）
という置き方にした。緩くても「20 倍遅くなった」は捕まえられる。

## 後回しにできる条件

並列化を後回しにできるのは**後から入れられる形を保っている場合だけ**である。
条件は「同じ音声を設定違いの複数インスタンスへ流せること」。
ユニットレベルの可変グローバルが 1 つでもあると、その時点で C-06 が
できなくなる。

監査した結果:

| 箇所 | 判定 |
|---|---|
| `RttyModemImpl` の `UOSTx` / `UOSRx` | **違反。インスタンスフィールドへ移した**（後述） |
| `ComplexFFT` | 引数内で完結し再入可能 |
| `TFftFilt` | インスタンスごと。並列可 |
| `PortAudioSoundDevice` の参照カウント | ライブラリ仕様上グローバルが必然。ロック済み |
| `EventBus` | 発行は任意スレッドから安全 |

`UOSTx` / `UOSRx`（Unshift On Space）は fldigi の `progdefaults` をそのまま
持ち込んでいたため全インスタンス共有だった。**送信用と受信用のインスタンスが
設定を共有する不具合**でもあったので、インスタンスフィールドへ移した。
`test_evidence.lpr` の 5 番でこの規律を固定している。

したがってこの ADR の対価は「状態をインスタンスに閉じ込める規律を常に守る」
ことであり、違反を見つけ次第つぶす。

## v1.1 への影響

| 要求 | 変更 |
|---|---|
| X-02 Worker Pool / Task Queue | Phase 1 → **Phase 3 で必要性が実測されてから** |
| X-03 CPU core 数に応じた Worker 数調整 | 同上 |
| C-10 SIMD 等の DSP 最適化 | 優先度を下げる。0.82% を 0.4% にしても誰も得をせず、Algorithm Portfolio で捨てるコードを最適化することになる |
| X-01 Audio I/O を DSP 重処理から分離 | **前倒しで要る**（並列化ではなく構造） |
| X-06 History Buffer | **前倒しで要る**（Replay の前提） |
| Z-04 Deterministic Realtime | **C-08 より優先**。判定を deadline 比に置いた |

X-08「資源に応じて調整する」は残すが、発動条件を「実測で足りなくなったとき」
に絞る。

## 付随して分かったこと: `TThread.ProcessorCount` が信用できない

```
TThread.ProcessorCount        = 1
sysconf(_SC_NPROCESSORS_ONLN) = 4
/proc/cpuinfo の processor 行 = 4
```

X-03 を FPC の標準 API で素直に書くと、この環境では Worker が 1 本になる。
実装時期を後ろ倒しにしたので当面は影響しないが、着手時には自前の検出が要る。
`nproc` は affinity マスクは見るが **cgroup の CPU quota は見ない**ため、
X-07（CPU / Memory / Latency / Power の検出）では quota も読む必要がある。

## 代替案と却下理由

**いま Worker Pool を作っておく。** 使う予定のない抽象を先に作ると、
Phase 3 で実際の要求が判明したときに形が合わず作り直しになる。
0.82% という数字は「急いで作る理由がない」ことを示している。

**「スレッドセーフ」を方針名にする。** 上述のとおり、スレッドを増やす方向に
働くため採らない。
